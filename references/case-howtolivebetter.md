# 案例：howtolivebetter.net

## 迭代过程（按时间）

1. **10-03 手动验证码版**：发「登录生活」→ 公众号回 6 位码 → 回网站输入。能用，但要来回切。
2. **10-04 下载口令**：下载弹窗给一个 4 位数字口令，发给公众号直接拿下载链接。
3. **关键词缩短**：「登录生活」→「生活」。
4. **10-07 配对码**：网站先给 6 位码，用户发过去，网站自动登录。不用再回来输码。
5. **微信内置浏览器专门处理**：不显示配对码，改成「发关键词 → 点一键登录链接」，并记住原页面，登录后跳回去。
6. **长按识别提示**：微信里看到二维码扫不了，加一句「长按识别」。
7. **手机浏览器**：先给码，「复制登录码并打开微信」按钮。
8. **底部同步停靠卡片**：标记达到 1/3/10/30/60/100 条时出现，可以收起成细条。

## 踩过的坑

- **配对码被报「已过期」**：应用层用 JS 时间和数据库时间比较，ORM 改了时间戳解码。改成在 PostgreSQL 里算 `expires_at > now()`。
- **微信内置浏览器配对失败**：用户去公众号发消息再点链接回来，开的是新页面，原页面的轮询早没了。所以微信内改走一键登录链接。
- **按 IP 限流误伤**：站点在 Cloudflare 后面，`x-forwarded-for` 拿到的是 Cloudflare 边缘 IP，按它限流不准。改成按账号或浏览器 cookie 限流，回调端拿到的是 account/browser key 而不是 IP。
- **自动回复失效**：启用消息推送前把 7 组关键词回复和欢迎语迁进了代码；菜单没有接口权限，改成发送「关于作者」触发。
- **老用户误建新号**：先用邮箱注册的人又用微信登录，会生成第二个账号。后来加了「这个微信之前单独登录过，要合并吗」，列出两边的进度条数让用户自己决定。
- **手动输码容易错**：统计期内 `wechat_code_error` 共 4,707 次。配对码上线后，手动输码只作为兜底。
